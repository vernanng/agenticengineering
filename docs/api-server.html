API server: how it works

The Fastify hub (server.ts) sits between the browser chat client and the muse serve subprocess. The host facade (host.ts) holds sessions, parks approval decisions, and fans SDK notifications out to browsers. Config comes only from .env (PORT, museBin, workspaceRoot).

1 · Where everything lives

Left to right: the browser posts turns and opens one GET /events stream per session; the hub validates, maps errors (404 unknown session, 410 stale approval, 400 bad input), and serves client/dist; the facade routes each call to its session, and the SDK multiplexes one muse serve child. Notifications flow back along the dashed path to every listening tab.

2 · A turn, end to end

Before any turn, the browser opens GET /events: the hub runs snapshot() first (a stale session fails 404 before headers), then streams ready, snapshot, and the live tail — one session only, plus a : ping every 25 s. The turn/ended push is emitted from turn.completed too, so a terminal the broadcast never carried still reaches the tab. Every response carries x-response-time.
